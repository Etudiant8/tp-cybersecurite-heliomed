1.Cadre et architecture du labo

HelioMed, PME éditant une plateforme de prise de RDV médicaux (Flask/Nginx/PostgreSQL, 2 serveurs Linux, données de santé RGPD). Le labo reproduit cette architecture avec OWASP Juice Shop (interface patient) et DVWA (composant applicatif de test) comme cibles d'entraînement.

Connectivité vérifiée Ping helio-frontal ↔ helio-applicatif : 4/4 paquets reçus, 0% de perte (2,4 – 5,0 ms). Voir capture console §3 et outputs/exercice1/preuve_vm_reseau.txt.

Interne négligent/malveillantErreur, vengeance, revente d'accèsAccès légitime, télétravail

Scénarios stratégiques

1. Vol de données de santé via compromission de la BDD

Cybercriminel opportuniste → BDD (données patients) → exploitation d'une CVE image non patchée (Trivy) ou d'une faille de configuration (ZAP) sur l'appli patient → pivot applicatif → exfiltration.

2. Rançongiciel via poste de développeur en télétravail

Cybercriminel opportuniste → disponibilité plateforme → phishing développeur → accès Git/déploiement compromis → charge malveillante.

3. Abus d'accès interne par un prestataire

Interne négligent/malveillant → confidentialité données patients → accès légitime mal cloisonné → export massif.

4. Usurpation d'un serveur HelioMed via clé SSH clonée constaté, pas théorique

nmap révèle que les deux serveurs partagent la même clé hôte SSH (clonage sans régénération) → un attaquant interne peut usurper l'un des deux sans alerte client → MITM ou redirection de trafic admin.

Pourquoi ces outils, sur ce périmètre

Nmap — a révélé un risque d'infrastructure (clés SSH dupliquées, Samba superflu) invisible aux scanners applicatifs : indispensable en amont de tout scan ciblé.

OWASP ZAP (passif) — adapté à l'interface patient : détecte les failles de configuration HTTP sans risquer de perturber un service manipulant potentiellement des données de santé. A remonté 116 alertes Medium directement exploitables.

Trivy — HelioMed est conteneurisé : les CVE dans les dépendances sont un risque direct invisible sans SCA. Complète ZAP en couvrant la chaîne d'approvisionnement logicielle.

Non retenus pour cette étape — Nikto (redondant avec ZAP, moins adapté aux SPA) et Burp Suite (usage manuel, moins reproductible pour une preuve automatisée).

10.Incident rencontré et résolution

Documenté ici en détail car il illustre une compétence transférable : le diagnostic de cause racine.

Symptôme Pendant apt-get install docker.io, le noyau de helio-applicatif a paniqué (« Fatal exception in interrupt »). Après redémarrage, les VM se sont mises en pause de façon répétée.
Fausse piste initiale Diagnostic orienté à tort vers un manque de RAM/CPU (VM à 1 vCPU/1,5 Go) — l'augmentation des ressources (2 vCPU/2 Go) n'a pas résolu le problème, seulement déplacé le symptôme (pauses au lieu de panic).
Cause racine réelle Le disque C: de l'hôte était à 0 octet libre (475 Go utilisés). Les écritures sur le disque virtuel (.vdi) de la VM échouaient silencieusement pendant l'extraction des paquets Docker, provoquant le panic. Correction : suppression de 3 dossiers de VM orphelins non enregistrés dans VirtualBox (Win client 17,8 Go, debian 8 Go, PFsense 0 Go) → 25,75 Go libérés. Nouvelle tentative : succès immédiat, aucun crash.
Second symptôme du même type (Trivy) Le scan Trivy de l'image Juice Shop timeout après 10, puis 20, puis 40 minutes depuis l'hôte Windows, alors que réseau et disque étaient sains. Cause probable : interception par l'antivirus Windows Defender lors de l'extraction de milliers de petits fichiers node_modules (paramètre système que je n'ai pas la permission de modifier). Contournement : installation de Trivy directement dans helio-applicatif et scan des images déjà présentes localement — résultat en moins de 3 minutes.

12.Conclusion

L'analyse de l'environnement HelioMed révèle un profil de risque cohérent avec une plateforme jeune et rapidement déployée : la surface applicative (DVWA en particulier, 805 CVE) et les défauts de configuration réseau/infrastructure (clés SSH dupliquées, Samba superflu) constituent les points d'attention prioritaires, avant même les vulnérabilités applicatives classiques détectées par ZAP. Les 5 objectifs de sécurité formulés (§7) adressent directement ces constats et serviront de fil conducteur aux exercices suivants du TP.
