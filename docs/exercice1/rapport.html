1.Cadre et architecture du labo

HelioMed, PME éditant une plateforme de prise de RDV médicaux (Flask/Nginx/PostgreSQL, 2 serveurs Linux, données de santé RGPD). 6.EBIOS Risk Manager (ANSSI) — Étape 1.3

Source de risqueMotivationRessources/capacités
Cybercriminel opportunisteGain financier (revente données santé, rançongiciel)Automatisé, scanners connus
Acteur ciblé (concurrent)Espionnage, déstabilisationCiblé, compétences moy./élevées
Interne négligent/malveillantErreur, vengeance, revente d'accèsAccès légitime, télétravail

Chaque scénario nomme une partie prenante intermédiaire explicite dans le chemin d'attaque.

  • 1. Vol de données de santé : cybercriminel → mainteneur tiers d'une image Docker publique → BDD → CVE héritée non patchée ou faille config (ZAP) → pivot → exfiltration.
  • 2. Rançongiciel télétravail : cybercriminel → poste personnel du développeur (BYOD) → disponibilité → phishing → accès Git/déploiement compromis → charge malveillante.
  • 3. Abus d'accès interne : interne malveillant → prestataire infogérance, accès VPN/SSH mutualisé → confidentialité → accès mal cloisonné, non attribuable → export massif.
  • 4. Usurpation via clé SSH clonée constaté, pas théorique — interne/ciblé → poste d'admin du prestataire (origine du clonage VM) → nmap révèle la clé hôte SSH partagée entre les 2 serveurs → usurpation sans alerte client → MITM / redirection trafic admin.

Nmap a révélé un risque d'infra (clés SSH dupliquées, Samba superflu) invisible aux scanners applicatifs. ZAP (passif) est adapté à l'interface patient sans risquer de perturber un service de santé (116 alertes Medium exploitables). Trivy couvre la chaîne d'approvisionnement logicielle, angle mort des deux autres outils. Non retenus : Nikto (redondant avec ZAP), Burp Suite (usage manuel, moins reproductible).

10.Incident rencontré et résolution

SymptômePendant apt-get install docker.io, le noyau a paniqué (« Fatal exception in interrupt »). Après reboot, pauses répétées.
Fausse pisteRAM/CPU insuffisants supposés — l'augmentation (1→2 vCPU, 1,5→2 Go) n'a fait que déplacer le symptôme (pause au lieu de panic).
Cause racine réelleDisque C: hôte à 0 octet libre (475 Go utilisés) → écritures .vdi en échec. Correction : suppression de 3 VM orphelines non enregistrées (25,75 Go libérés) → succès immédiat.
Second incident du même type (Trivy) Scan Juice Shop en timeout après 10/20/40 min depuis l'hôte alors que réseau et disque étaient sains — cause probable : interception antivirus (Windows Defender) sur des milliers de fichiers node_modules, paramètre système hors de ma permission de modification. Contournement : Trivy installé et exécuté dans helio-applicatif sur les images déjà locales — résultat en moins de 3 minutes.

12.Conclusion

L'analyse révèle un profil de risque cohérent avec une plateforme jeune et rapidement déployée : la surface applicative (DVWA, 805 CVE) et les défauts d'infrastructure (clés SSH dupliquées, Samba superflu) sont prioritaires, avant même les vulnérabilités applicatives classiques détectées par ZAP. Les 5 objectifs de sécurité (§7) adressent directement ces constats et guideront les exercices suivants du TP.
